sbom-audit

Claude Code plugin, version 1.4.1

Know what every repository in a folder is built from, and whether today's advisory touches it.

It reads the committed branches of every repo (main and dev by default), never your working copy, writes one software bill of materials per project and branch, checks it against the public vulnerability databases, and leaves the evidence in a security/ folder with its own history. Claude does the part the databases cannot: the sweep for incidents that are too fresh, the triage, and a written assessment with actions per project.

What it can do

Ten skills, one knowledge skill and a session reminder. Everything runs locally; the only things sent out are package names, versions and advisory ids, to the databases named above, plus repository names to GitHub, and SSH to the servers you list if you turn on host mode. No source code, no SBOM file and no secret value leaves the machine.

/sbom-audit:setup

Finds every repository under the folder you are in, writes security/sbom-audit.toml and starts the security/ folder, as its own git repository if you ask. It can also turn on Dependabot alerts for your GitHub projects, but only after it has shown you the list and you rerun it with --yes.

/sbom-audit:run

One SBOM per project and branch. Vulnerabilities from OSV.dev, the actively exploited ones marked from CISA KEV, each CVE's EPSS score, end-of-life runtimes and base images, direct dependencies that are majors behind, and an incremental secrets scan. It writes STATUS.md and issues.json, the list of every open issue and where it occurs for whoever fixes it, then Claude reads the report and writes the assessment.Minutes for ten repositories. Run it in the background.

/sbom-audit:incident CVE-2021-23337

Fetches the affected versions from OSV and gives a verdict per project, branch and installed version. Takes a CVE, GHSA or PYSEC id (a bare package name lists where it is used, without a verdict) and is what “are we affected by …” should go to. Exits 1 on a hit, 2 when it cannot answer, so a script can key on it.

/sbom-audit:lookup 'expo-*' nginx:alpine nodejs

Who uses what, from the last scan, in a second. Package names, globs, container images and runtimes all work.

/sbom-audit:vex

Records why a finding does or does not apply, as an OpenVEX statement per project. Every later run honours it and lists what it suppressed, so the counts stay honest. incident --vex records the no-hits in one go.

/sbom-audit:status

Prints STATUS.md, the one-screen summary of the last run: what failed, what is new since the run before, open secrets, the scheduler and whether an assessment is waiting. Writes nothing.

/sbom-audit:assess

Turns a run into a written ## Assessment: an incident sweep for the runtimes and frameworks you use, the fixed triage order, actions per project, and one list of drafted VEX statements and secrets decisions. A second agent tries to disprove every decision that would close a finding, and the list is written only after you confirm it.

/sbom-audit:secrets

Scans every repository's git history with gitleaks, locally, and ranks findings in classes A, B and C. SECRETS.md names each finding by fingerprint, file and line, never by value; resolve records a decision after you confirm it.

/sbom-audit:hosts

Optional. Checks the Debian and Ubuntu servers you list, installing nothing on them, over SSH with a forced-command audit login: open updates against OSV and CISA KEV, the patch automation itself, a state fingerprint against the baseline you accepted, SSH logins and a Lynis hardening index, written to HOSTS.md. patch, bootstrap and unbootstrap print a plan first and run only after you name the host and confirm it.

/sbom-audit:schedule weekly

Runs the audit every Saturday at 03:00 through launchd or a systemd user timer on this machine; off removes it. A missed week shows up in the session reminder.

Session reminder

A hook prints one line from security/status.json when a session starts: a failed or overdue run, a missed weekly schedule, open class A secrets, new KEV or CRITICAL/HIGH findings. It never runs anything on its own.

How a run works

  1. Read, do not touch

    After a git fetch, each branch is exported with git archive. No checkout, nothing written into the audited repositories. The working tree is ignored on purpose: HEAD is often a feature branch, while main and dev are what ships.

  2. Catalogue

    Syft writes a CycloneDX SBOM per project and branch. The plugin's own readers add what Syft cannot see: runtimes from engines and requires-python, images from Dockerfiles and compose files, the Supabase edge runtime and Postgres version from config.toml, and packages that a deno.lock pulls from esm.sh and similar CDNs.

  3. Match

    osv-scanner checks every package version against OSV.dev, which aggregates GitHub advisories, PyPI advisories and the NVD.

  4. Enrich

    The CISA catalogue of known exploited vulnerabilities marks what is used in real attacks. FIRST's EPSS scores estimate how likely a CVE is to be exploited in the next 30 days; a MEDIUM or LOW finding in production or a supported release at or above 10% moves up to the critical and high rank, and a score never moves anything down. endoflife.date dates every runtime and base image. npm, PyPI and JSR say how many major versions behind each direct dependency is. A lookup that fails is reported as failed, retried next run, and never shown as clean.

  5. Apply your decisions

    OpenVEX statements under security/vex/ suppress what you have already judged. The report lists exactly what they suppressed.

  6. Write it down

    AUDIT.md for people, audit.json for scripts, INVENTORY.md and inventory.json for what is installed where, a dated copy under reports/, and one line in log.md. Earlier assessments are carried over. The first table in the report is the status of every source.

  7. Assess

    Claude reads the source status first, searches the web for advisories of the last 30 days across every runtime and framework in your inventory, runs incident for each one, triages in a fixed order and appends an assessment with actions per project: manifest, package, current version, target version. Remediation is then one pull request per project, with that project's tests.

The triage order never changes

  • Class A secrets, then KEVA leaked admin key or an exploit in the wild. Fix before anything else.
  • Critical and high in productionProjects marked production = true come first; class B secrets and findings likely to be exploited by EPSS rank here too.
  • End-of-life runtimes and imagesNo more security patches, whatever the scanner says today.
  • Floating image tagslatest and alpine rebuild to whatever is current.
  • Dev-only toolingLabelled as such and counted separately, never inflated.

Verdicts you can act on

An incident query answers per project, branch and installed version, with the evidence next to it. Four verdicts exist:

hit: the vulnerable version is installed present, not affected: installed outside the affected range, or a VEX statement covers it absent: not in that branch's SBOM unknown: that branch's last audit was incomplete, run again before trusting it

What leaves your machine

The plugin's own scripts send no source code, no SBOM file and no secret value anywhere. The outbound hosts are public databases, your own remotes and servers, and Anthropic; each gets only what the table says.

gitleaks runs locally and makes no network calls: no verification of found credentials, no telemetry. During the assessment Claude searches the web for incidents of the last 30 days; the queries name the runtimes and frameworks in your inventory, not your projects.

Install

Claude Code, Python 3.11 or newer with the standard library only, and four tools from Homebrew. Git is assumed. Without gitleaks the secrets scan reports skipped, never clean.

brew install syft osv-scanner gitleaks gh
claude plugin marketplace add Wuesteon/sbom-audit
claude plugin install sbom-audit@wuesteon-plugins

cd ~/projects && claude       # the folder that holds your repositories
# then, inside Claude Code:
/sbom-audit:setup --init-git  # once
/sbom-audit:run               # a few minutes; ends with STATUS.md and an assessment

Exit codes of run: 0 clean, 1 findings present, 2 a source failed and its section is empty rather than clean, 3 a malformed VEX file, 4 a required tool is missing, checked before anything is written, 5 read-only mode (SBOM_AUDIT_READ_ONLY=1), nothing written.
